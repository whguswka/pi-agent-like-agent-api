# 프로젝트 하네스 맞추기

모델이 같은 실수(시험을 다 하지 않고 '완료', 찌꺼기를 남김, 공통함수를 다시 만듦, 운영 코드를 고침)를 되풀이하지 않게,
팀 저장소에 네 가지를 만든다. 지침의 '하지 말 것' 보다 실행해서 확인하는 장치가 잘 듣는다.

| 만들 것 | 위치 | 하는 일 |
|---|---|---|
| 점검 스크립트 | 저장소의 `tools/check_*.py` 등 | 바뀐 것이 팀 표준에 맞는지, 시험을 끝까지 했는지, 남긴 것이 없는지 보고 종료 코드로 알림 |
| 완료 점검 설정 | 저장소의 `.pi/checks.json` | 요청이 끝날 때 키트가 점검 스크립트를 돌리고, 실패하면 pi 에게 한 번 돌려줌 (키트 훅 `checks`) |
| 팀 표준 스킬 | 저장소의 `.pi/skills/<이름>/SKILL.md` | 새로 만들기·고치기·시험·반영 절차를 일할 때 볼 만큼만 |
| 규칙·설정 | 저장소의 `AGENTS.md`, 내 설정 파일 `bridge.json` | 운영 영역은 읽기만, 승인이 필요한 일. `guard_readonly`·`guard_patterns` 값 |

같은 폴더의 `examples/` 에 모델 운영 저장소(모델 12개, 5단계, 공통 모듈, 개발·운영 트리)로 만든 예가 있다:
`check_standard.py`(점검 스크립트), `checks.json`, `team-skill.example.md`(팀 표준 스킬), `AGENTS.example.md`.
구조가 다르면 예를 베끼지 말고 이 저장소의 실제 이름·경로·함수로 쓴다.

## 순서
1. 읽는다 (통째로 읽지 말고 `find`·`grep -n` 으로 찾아 필요한 부분만):
   표준·안내 문서, 공통 모듈 목록과 주요 함수의 인자, 비슷한 단위(모델 등) 두세 개, 실행 방법(단계·파이프라인), 관리 테이블을 쓰는 코드,
   운영 반영 절차(복사·동기화 스크립트, 파이프라인 등록), 시험 데이터가 운영과 갈리는 방법(환경 변수, 트리, 스키마).
2. 사용자에게 확인한다: 운영 영역이 어디인지(폴더·브랜치·네임스페이스), 승인이 필요한 일, 시험해도 되는 영역. 모르는 것은 추측하지 말고 묻는다.
3. 점검 스크립트를 쓴다 (아래 '점검할 것', '실패 줄 쓰는 법').
4. 손으로 돌려 본다: 지금 상태에서 한 번, 일부러 하나를 깨뜨려(설정 항목 하나 빼기 등) FAIL 이 나오는지 한 번. 깨뜨린 것은 되돌린다.
5. `.pi/checks.json`, 팀 표준 스킬, `AGENTS.md` 몇 줄을 쓰고, 내 설정 파일에 넣을 값(`guard_readonly`, `guard_patterns`)을 알려 준다.
   내 설정 파일은 사용자의 것이므로 고치기 전에 묻는다.
6. 만든 것과 시험 결과, 사용자가 할 일(커밋, 팀에 알리기, 처음 점검할 때 실행 허락)을 정리한다.

## 점검할 것
바뀐 것만 본다 (운영에 아직 반영하지 않은 변경: 운영 쪽 커밋·브랜치와 비교한 차이와 새 파일). 공통 모듈이 바뀌었으면 모든 단위를 본다.
- 구조: 단위마다 있어야 할 파일, 설정의 필수 항목과 값의 범위.
- 공통함수만 쓰는지: S3·DB·관리 테이블을 직접 쓰는 코드, 공통함수가 하는 계산(학습일 등)을 다시 만든 코드.
- 시험 증거: 고친 뒤에 끝까지 마친 시험 실행이 있는지 (관리 테이블·로그로). 공통함수가 바뀌면 모든 단위.
  계산 규칙(학습일 등)을 바꿨으면 그 규칙이 실제로 쓰이는 경우(학습일 시험)도.
- 남긴 것: 끝나지 않은 실행 기록, 지우지 않은 임시 파일·데이터, 이번 시험의 산출물.
- 공통함수의 예전 호출이 그대로 되는지 (표준이 호환을 요구하면): 점검 스크립트에서 예전 꼴로 한 번 불러 본다. 지침에만 적으면 모델이 지나친다
  (2026-10-24 비교 시험: Claude Code 는 2번 모두 예전 호출을 살렸고 pi 는 2번 모두 없앰).
- 새로 만든 도구(`tools/` 등)는 사용자가 쓸 그대로(인자 없이) 한 번 실행해 종료 코드 0 인지. 운영 상태를 보는 도구면 기본이 운영인지
  (같은 시험: 인자 없이는 개발 기록을 보여 줘 '운영 상태' 요청과 어긋남. 지침 한 줄로는 4번 중 3번 그대로였음). 예: `examples/check_standard.py` 의 `check_tool_run`.
  - 인자 없이 돌려도 안전한 읽기 도구일 때만 돌린다. 쓰거나 지우는 도구가 있는 저장소면 이름으로 거른다. 도구마다 시간 한도(예 60초)를 둔다.
  - 출력으로 보는 점검('운영 기록이 있는데 출력에 실행 결과가 없음')은 개발 기록이 비어 있을 때만 확실하다. 코드 점검('운영을 보는 곳이 없음')과 함께 쓴다.
  - 출력의 빈 칸이 맞는지도 본다. 예: 다음 학습일 칸이 '-' 인 모델 (2026-10-25 시험: 마지막 학습일이 빈 모델 3개의 다음 학습일을 비움. 그 칸이 비면 안 되는 이유는
    팀이 알므로, 실패 줄에 무엇으로 채울지(학습 주기로 오늘부터 셈)를 적는다). 예: `examples/check_standard.py` 의 `blank_next`.
- 실패가 아닌 '알림': 승인이 필요한 일(등록, 운영 반영). 알림만 있으면 종료 코드 0.

## 점검이 돌지 않는 일
- 파일을 바꾸지 않는 요청(원인 찾기, 조회)은 완료 점검이 돌지 않는다. 같은 시험에서 pi 는 원인 찾기 2번 모두 오류 메시지만 읽고 코드를 열지 않았다.
  팀 표준 스킬·`AGENTS.md` 에 '원인은 코드 위치(파일·줄)와 다른 단위 영향을 함께' 를 적는다. 키트도 늘 넣는 지침으로 '원인은 코드를 읽어 근거 위치와 함께' 를 알린다.
- 운영을 바로 고쳐 달라는 요청: `AGENTS.md` 에 '거절만 하지 말고 개발 영역에서 고치고 시험한 뒤 반영 승인을 묻는다' 를 적는다 (`guard_readonly` 가 실제 쓰기를 막음).

## 실패 줄 쓰는 법
- 한 줄에 무엇이 틀렸는지와 **고칠 명령을 그대로** 쓴다. 모델은 실패 줄의 명령을 거의 그대로 쓴다.
  예: `끝나지 않은 시험 실행 run 184 (2026-09-01): 같은 날짜로 남은 단계를 이어서 끝내거나, 버릴 실행이면 python -c "from common import registry; registry.register_end(184, 'FAILED', message='시험 중단')"`
- 고치는 방법이 또 찌꺼기를 남기지 않게 쓴다. '단계를 따로 먼저 돌려라' 는 끝나지 않은 실행을 남겼다 → '5단계 전체를 그 날짜로' 처럼 끝까지 도는 명령으로.
- 지워도 되는 것(이번 시험이 남긴 임시 데이터)은 지우는 명령을 적는다. 승인이 필요한 일은 FAIL 이 아니라 '알림' 으로.
- 출력은 단위마다 몇 줄로 짧게, 끝에 `결과: 통과` 또는 `결과: 고칠 것이 있음 (n개)`. 고칠 것이 있으면 종료 코드 1.
- 시각을 적으면 시간대(UTC 등)가 관리 테이블과 같게.

## `.pi/checks.json`
```json
{"checks": [{"name": "모델 표준 점검", "when": ["models/**", "common/**", "tools/**"], "run": "python tools/check_standard.py --changed", "timeout": 180}]}
```
- `when` 은 작업 폴더 기준 경로 패턴. 이 요청에서 맞는 파일이 바뀌었을 때만 돈다. `run` 은 작업 폴더에서 bash 로 돈다.
- 처음 돌 때 사용자에게 실행해도 되는지 묻는다 (프로젝트·명령마다 한 번). 끄기: `/hooks off checks`.
- 오래 걸리는 시험(모델 학습 등)은 점검 명령에서 돌리지 말고, 시험한 증거만 본다 (`timeout` 은 최대 600초).

## 팀 표준 스킬
- 표준 문서를 다 옮기지 말고 일할 때 볼 것만: 새로 만들기 순서, 시험 명령, 공통함수 바꿀 때 순서, 운영 반영 절차, 승인이 필요한 일.
- 시험에서 모델이 헤맨 곳을 적는다. 예: 새 모델은 학습한 모델이 없으므로 첫 시험은 가장 최근 학습일로 5단계 전체 → 그다음 최근 영업일.
- 점검 스크립트를 적어 둔다: 끝내기 전에 `python tools/check_standard.py --changed`.
- `description` 에 쓰는 때를 적는다 ("새 모델을 만들거나 모델·공통함수를 고칠 때 사용").

## 규칙·설정
- `AGENTS.md`: 운영 영역은 읽기만, 반영은 승인 뒤 정해진 절차로만, 시험은 개발 영역에서. 몇 줄로.
- `guard_readonly`: 운영 코드가 폴더면 그 폴더 (예: `["~/work/model-lab-prod"]`). 그 안의 파일 쓰기와 그 안에서 실행하는 프로그램을 묻는다.
- `guard_patterns`: 운영 반영이 명령이면 그 명령 (예: 반영 스크립트, 파이프라인 등록 `upload_pipeline`, 정기 실행 등록 `create_recurring_run`, 운영 브랜치 push).
